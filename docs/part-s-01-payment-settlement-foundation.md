# Part S Batch 01 — Payment Settlement Foundation

## Purpose

Part S closes the gap between order lifecycle truth and payment settlement truth.

Before this batch, checkout creates a payment record (COD starts as `UNPAID`) and the admin order page can display it, but there is no audited admin mutation path for payment reconciliation.

## Payment lifecycle

Allowed admin transitions are deliberately constrained:

- `UNPAID` → `PENDING`, `PAID`, `FAILED`
- `PENDING` → `UNPAID`, `PAID`, `FAILED`
- `FAILED` → `UNPAID`, `PENDING`, `PAID`
- `PAID` → `REFUNDED`
- `REFUNDED` is terminal

The `PENDING → UNPAID` and `FAILED → UNPAID` paths support reconciliation/correction without deleting history.

## Mutation boundary

Only these roles may mutate settlement:

- `OWNER`
- `ADMIN`
- `ORDER_MANAGER`

`ANALYST` remains read-only.

Every mutation is guarded by:

1. current store + order identity,
2. latest payment identity,
3. expected payment revision,
4. expected payment status,
5. a database transaction with row locks.

A newly-created or concurrently-changed latest payment therefore fails closed instead of silently updating a stale row.

## Atomic consistency

A successful reconciliation updates in one transaction:

- latest `payments.status`,
- latest `payments.provider_reference`,
- `payments.revision`,
- denormalized `orders.payment_status`,
- immutable `payment_status_history`.

Payment method, amount and currency are not mutable through this feature.

## Audit history

Each payment status change records:

- payment/order/store identity,
- before + after status,
- before + after provider reference,
- optional reconciliation note,
- admin actor,
- timestamp.

The audit table uses RLS and remains append-only through the application path.

## Financial-recognition boundary

**S01 does not change Part Q/R profitability recognition yet.**

That change belongs to S02. Until S02 is completed, existing delivered-order contribution logic continues to use order lifecycle semantics.

S01 establishes trustworthy settlement data first so S02 can safely make revenue recognition payment-aware.

## Migration

S01 claims migration `0019`.

It adds:

- `payments.revision` with default `0`,
- nonnegative revision constraint,
- `payment_status_history`,
- RLS + supporting indexes/FKs.

No `0020` migration should be generated by this batch.
